# 02 Software Requirements Specification (SRS)  
**Project:** Campus Lost & Found Management System  
**Version:** 1.0  
**Date:** 30.08.26

---

## 1. Introduction

### 1.1 Purpose
এই ডকুমেন্টটি **Campus Lost & Found Management System**-এর কার্যকরী ও অ-কার্যকরী প্রয়োজনীয়তাগুলো বিস্তারিতভাবে বর্ণনা করে। এটি ডেভেলপমেন্ট টিম, প্রজেক্ট সুপারভাইজার এবং স্টেকহোল্ডারদের জন্য একটি রেফারেন্স হিসেবে কাজ করবে, যাতে সিস্টেমের প্রতিটি ফিচার ও আচরণ স্পষ্টভাবে সংজ্ঞায়িত থাকে।

### 1.2 Scope
সিস্টেমটি একটি বিশ্ববিদ্যালয় ক্যাম্পাসের মধ্যে হারানো ও পাওয়া জিনিসপত্র ব্যবস্থাপনার জন্য একটি ওয়েব-ভিত্তিক প্ল্যাটফর্ম। এর মূল লক্ষ্য:
- শিক্ষার্থীদের যাচাইকৃত পোস্ট তৈরি করার সুযোগ দেওয়া।
- হারানো ও পাওয়া আইটেমের তথ্য সংগঠিতভাবে প্রদর্শন।
- একটি নিয়ন্ত্রিত দাবি (Claim) প্রক্রিয়া, যেখানে প্রশাসক চূড়ান্ত সিদ্ধান্ত নেয়।
- পোস্টের জীবনচক্র ট্র্যাক করা (Open → Claimed → Resolved)।

প্রজেক্টটি একটি বিশ্ববিদ্যালয়ের ল্যাব প্রজেক্ট হিসেবে তৈরি হবে। এতে ফুল-স্ট্যাক ওয়েব অ্যাপ্লিকেশন থাকবে, তবে মোবাইল অ্যাপ বা রিয়েল-টাইম চ্যাট-এর মতো ফিচার এই সংস্করণে অন্তর্ভুক্ত নয়।

### 1.3 Definitions, Acronyms, and Abbreviations
| শব্দ | সংজ্ঞা |
|------|--------|
| **Lost** | কোনো আইটেম হারিয়ে গেছে — পোস্টকারী মালিক। |
| **Found** | কোনো আইটেম পাওয়া গেছে — পোস্টকারী সেটি খুঁজে পেয়েছেন। |
| **Claim** | কোনো ইউজার কর্তৃক একটি Found পোস্টের আইটেমের মালিকানা দাবি করা। |
| **Admin** | সিস্টেম প্রশাসক, যিনি ইউজার ভেরিফিকেশন, পোস্ট মডারেশন ও দাবি নিষ্পত্তি করেন। |
| **Guest** | লগইন না করা ভিজিটর, শুধু দেখতে ও সার্চ করতে পারে। |
| **Verified Student** | অ্যাডমিন কর্তৃক অনুমোদিত শিক্ষার্থী, যিনি পোস্ট ও দাবি করতে পারেন। |
| **SRS** | Software Requirements Specification |

### 1.4 References
- প্রজেক্ট প্রবলেম স্টেটমেন্ট (পূর্বে তৈরি)
- ওয়েব ইঞ্জিনিয়ারিং টেকনোলজি ল্যাব প্রজেক্ট গাইডলাইন
- MongoDB, Express, Node.js ডকুমেন্টেশন (ইমপ্লিমেন্টেশনে ব্যবহৃত হবে)

## 2. Overall Description

### 2.1 Product Perspective
এটি একটি স্বতন্ত্র ওয়েব অ্যাপ্লিকেশন। এটি বিশ্ববিদ্যালয়ের বিদ্যমান কোনো সিস্টেমের সাথে সংযুক্ত নয়; বরং একটি ডেডিকেটেড প্ল্যাটফর্ম হিসেবে কাজ করবে। ভবিষ্যতে এটিকে বিশ্ববিদ্যালয়ের মূল পোর্টালের সাথে সংযুক্ত করা যেতে পারে।

### 2.2 Product Functions (Summary)
- ইউজার রেজিস্ট্রেশন ও লগইন (স্টুডেন্ট আইডি ভিত্তিক)
- অ্যাডমিন কর্তৃক ইউজার ভেরিফিকেশন
- Lost/Found পোস্ট তৈরি, দেখা, সম্পাদনা, মুছে ফেলা
- ছবি আপলোড
- সার্চ ও ফিল্টার
- Claim সাবমিশন ও অ্যাডমিন রিভিউ
- পোস্ট স্ট্যাটাস পরিবর্তন
- অ্যাডমিন ড্যাশবোর্ড

### 2.3 User Classes and Characteristics
| ইউজার ক্লাস | বৈশিষ্ট্য | প্রধান কাজ |
|-------------|-----------|------------|
| **Guest** | লগইন করেনি, শুধু ব্রাউজ করে | পোস্ট দেখা, সার্চ করা |
| **Verified Student** | স্টুডেন্ট আইডি দিয়ে রেজিস্টার্ড, অ্যাডমিন কর্তৃক অনুমোদিত | পোস্ট তৈরি/এডিট/ডিলিট, Claim করা, নিজের পোস্টের স্ট্যাটাস পরিবর্তন |
| **Admin** | সিস্টেম পরিচালক (ডামি অ্যাকাউন্ট) | ইউজার ভেরিফিকেশন, পোস্ট ডিলিট, Claim সময়সীমা নির্ধারণ ও নিষ্পত্তি |

### 2.4 Operating Environment
- **ক্লায়েন্ট সাইড:** আধুনিক ওয়েব ব্রাউজার (Chrome, Firefox, Edge)
- **সার্ভার সাইড:** Node.js runtime, MongoDB ডাটাবেস
- **নেটওয়ার্ক:** ইন্টারনেট / লোকালহোস্ট (ডেভেলপমেন্টের জন্য)

### 2.5 Design and Implementation Constraints
- প্রজেক্টটি **MERN-এর মতো স্ট্যাক** ব্যবহার করবে (MongoDB, Express, Node.js; ফ্রন্টএন্ডে HTML/CSS/JavaScript, React ঐচ্ছিক)।
- ইমেজ স্টোরেজ লোকাল সার্ভারে বা ক্লাউডে হতে পারে (তবে প্রাথমিকভাবে লোকাল)।
- পাসওয়ার্ড হ্যাশিং (bcrypt) ও JWT অথেনটিকেশন আবশ্যক।
- অ্যাডমিন প্যানেল সরল হতে হবে, জটিল অ্যানালিটিক্স নয়।

### 2.6 Assumptions and Dependencies
- বিশ্ববিদ্যালয়ের শিক্ষার্থীদের একটি নির্দিষ্ট ফরম্যাটে স্টুডেন্ট আইডি থাকে (যেমন: CSE-2022-001)।
- অ্যাডমিন একজন বিশ্বস্ত ব্যক্তি (ডেমোতে একটি নির্দিষ্ট অ্যাকাউন্ট)।
- ব্যবহারকারীরা সত্য তথ্য প্রদান করবে; অন্যথায় পোস্ট/অ্যাকাউন্ট ডিলিট করা হবে।
- ইন্টারনেট সংযোগ প্রয়োজন (লাইভ ডেমোর জন্য)।

## 3. Functional Requirements

### 3.1 User Authentication & Verification

#### 3.1.1 Registration
- সিস্টেমে নতুন ইউজার রেজিস্ট্রেশন ফর্ম পূরণ করবে।
- প্রয়োজনীয় ফিল্ড:
  - Full Name (পূর্ণ নাম)
  - Student ID (ইউনিক)
  - Email (ইউনিক, বিশ্ববিদ্যালয় ইমেইল হওয়া আবশ্যক নয় তবে পছন্দনীয়)
  - Phone Number
  - Department (ড্রপডাউন)
  - Batch (যেমন: 2022)
  - Password (কমপক্ষে ৬ অক্ষর)
- সাবমিটের পর ইউজারের স্ট্যাটাস হবে **Pending**।
- ইউজার তখন লগইন করতে পারবে না যতক্ষণ না অ্যাডমিন Approve করে।

#### 3.1.2 Login
- নিবন্ধিত ইউজার Student ID/Email ও পাসওয়ার্ড দিয়ে লগইন করবে।
- লগইন সফল হলে JWT টোকেন জেনারেট হবে এবং সেশন তৈরি হবে।
- শুধুমাত্র **Approved** ইউজার লগইন করতে পারবে। Pending/Rejected হলে যথাযথ এরর মেসেজ দেখাবে।

#### 3.1.3 Admin Verification
- অ্যাডমিনের ড্যাশবোর্ডে Pending ইউজারদের তালিকা দেখাবে।
- প্রতিটি ইউজারের তথ্য (Student ID, Name, Dept, Batch) দেখে অ্যাডমিন **Approve** বা **Reject** করবে।
- Reject করলে কারণ উল্লেখ করার অপশন থাকতে পারে (ঐচ্ছিক)।

### 3.2 Post Management

#### 3.2.1 Create Post
- শুধুমাত্র **Verified Student** পোস্ট তৈরি করতে পারবে।
- ফর্ম ফিল্ড:
  - Post Type: Lost / Found (রেডিও বাটন)
  - Item Name (টেক্সট)
  - Category (ড্রপডাউন: ID Card, Wallet, Phone, Book, Key, Other)
  - Description (টেক্সট এরিয়া)
  - Location (ড্রপডাউন: Library, Cafeteria, Dormitory, Academic Building, Playground, Other)
  - Date & Time (যখন হারিয়েছে/পাওয়া গেছে)
  - Images: সর্বোচ্চ ৩টি ছবি (jpg/png, max 2MB each)
  - Contact Information:
    - Email (প্রি-ফিল্ড হতে পারে)
    - Phone
    - Visibility: Public / Private (Public হলে সবাই দেখবে, Private হলে শুধু লগড-ইন ভেরিফাইড ইউজার দেখবে)
- সাবমিট করলে পোস্টের স্ট্যাটাস হবে **Open**।

#### 3.2.2 View Post
- হোমপেজে সব পোস্ট কার্ড আকারে দেখাবে (Lost/Found ব্যাজ, ছবি থাম্বনেইল, শিরোনাম, লোকেশন, তারিখ)।
- পোস্টে ক্লিক করলে বিস্তারিত পেজ খুলবে:
  - বড় ছবি (গ্যালারি)
  - সম্পূর্ণ বিবরণ
  - পোস্টকারীর নাম (ভেরিফাইড ব্যাজসহ)
  - যোগাযোগ বাটন (যদি পাবলিক হয় বা ভিউয়ার লগড-ইন থাকলে)
  - পোস্টের স্ট্যাটাস (Open/Claimed/Resolved)
  - Claim বাটন (যদি Found পোস্ট হয় এবং ভিউয়ার ভেরিফাইড হয়)

#### 3.2.3 Edit Post
- পোস্টকারী নিজের পোস্ট এডিট করতে পারবেন।
- সব ফিল্ড আপডেটযোগ্য, তবে Post Type পরিবর্তন করা যাবে না।
- ছবি যোগ/মুছে ফেলা যাবে।

#### 3.2.4 Delete Post
- পোস্টকারী নিজের পোস্ট ডিলিট করতে পারবেন।
- ডিলিট করলে সংশ্লিষ্ট ছবি, claim রেকর্ডও মুছে যাবে।

#### 3.2.5 Post Status Management
- পোস্টকারী নিজের পোস্টের স্ট্যাটাস পরিবর্তন করতে পারবেন:
  - Open → Resolved (যদি জিনিস ফেরত পেয়ে থাকেন বা ফেরত দিয়ে দেন)
  - Claimed → Resolved (অ্যাডমিন সিদ্ধান্ত নেওয়ার পর)
- Resolved পোস্ট হোমপেজ থেকে আড়াল হবে না, তবে একটি "Resolved" ব্যাজ দেখাবে এবং ডিফল্ট ফিল্টারে বাদ দেওয়া যাবে।

### 3.3 Search & Filter
- হোমপেজে একটি সার্চ বার থাকবে (কীওয়ার্ড: item name, description, location)।
- ফিল্টার অপশন:
  - Post Type: Lost / Found / All
  - Category
  - Location
  - Date Range (From – To)
  - Status: Open / Claimed / Resolved
- ফলাফল রিয়েল-টাইম আপডেট হবে (ক্লায়েন্ট সাইড বা সার্ভার সাইড)।

### 3.4 Claim System (নিয়ন্ত্রিত দাবি প্রক্রিয়া)

#### 3.4.1 Submit Claim
- লগইন করা ভেরিফাইড ইউজার একটি **Found** পোস্টে “Claim” বাটনে ক্লিক করতে পারবেন।
- একটি ছোট ফর্ম খুলবে যেখানে দাবিদার ব্যাখ্যা করবেন কেন তিনি মনে করেন জিনিসটি তার (যেমন: আইডি কার্ডের নাম, ব্যাচ, বিশেষ চিহ্ন)।
- সাবমিটের পর দাবিটি **Pending** স্ট্যাটাসে অ্যাডমিনের কাছে জমা হবে।
- একই পোস্টে একাধিক ইউজার দাবি করতে পারবেন।

#### 3.4.2 Admin Claim Review
- অ্যাডমিনের ড্যাশবোর্ডে সব Pending Claims দেখা যাবে।
- অ্যাডমিন প্রতিটি দাবি পরীক্ষা করে দেখবেন (দাবিদারের তথ্য, পোস্টের তথ্য)।
- অ্যাডমিন একটি **Timeline** নির্ধারণ করবেন (যেমন: ২ দিন, ৩ দিন) — এই সময়ের মধ্যে অন্য কেউ দাবি করতে পারবে।
- Timeline শেষ হলে অ্যাডমিন সব দাবিদারের তথ্য তুলনা করে **সঠিক মালিক** নির্বাচন করবেন।

#### 3.4.3 Timeline Setting
- অ্যাডমিন প্রতিটি Claim-এর জন্য একটি Deadline সেট করবেন (date + time)।
- Deadline-এর আগ পর্যন্ত পোস্টে নতুন Claim জমা হতে পারবে।
- Deadline পার হলে নতুন Claim বাটন অক্ষম হয়ে যাবে।

#### 3.4.4 Final Resolution
- অ্যাডমিন একটি নির্দিষ্ট দাবিকে **Accepted** করতে পারবেন; বাকিগুলো **Rejected** হবে।
- Accepted হলে পোস্টের স্ট্যাটাস **Resolved** হয়ে যাবে এবং পোস্টকারী ও দাবিদারকে নোটিফিকেশন পাঠানো হবে (ঐচ্ছিক)।
- পোস্টকারী চাইলে নিজেও Claim Accept করতে পারবেন যদি অ্যাডমিন সেটা অনুমোদন করে, কিন্তু মূল নিয়ন্ত্রণ অ্যাডমিনের কাছে থাকবে।

### 3.5 Admin Panel
- অ্যাডমিন একটি আলাদা ড্যাশবোর্ডে লগইন করবেন (নির্দিষ্ট ক্রেডেনশিয়াল)।
- **User Management:**
  - Pending Users list → Approve/Reject
  - All Users list → View, Delete (ঐচ্ছিক)
- **Post Moderation:**
  - All Posts list → View, Delete (অনুপযুক্ত পোস্ট সরাতে)
- **Claim Management:**
  - All Claims list (Pending, Accepted, Rejected)
  - প্রতিটি Claim-এর বিস্তারিত দেখে Timeline set করা
  - Accept/Reject বাটন

### 3.6 Notification (Optional / Should Have)
- ইউজারকে ইমেইল বা ইন-অ্যাপ নোটিফিকেশন পাঠানো হতে পারে:
  - রেজিস্ট্রেশন Approved/Rejected
  - নিজের পোস্টে কেউ Claim করলে
  - Claim Accepted/Rejected হলে
- এটি প্রাথমিকভাবে ইন-অ্যাপ (বেল আইকন) হিসেবে থাকলে ভালো, ইমেইল পরে যোগ করা যাবে।

## 4. Non-Functional Requirements

### 4.1 Performance
- পেজ লোড হতে সর্বোচ্চ ৩ সেকেন্ড সময় লাগবে (সাধারণ অবস্থায়)।
- সার্চ/ফিল্টার ফলাফল ১ সেকেন্ডের মধ্যে প্রদর্শিত হবে (ডেটাসেট ছোট হলে)।
- ইমেজ আপলোডের সময় ফাইল সাইজ ২MB পর্যন্ত গ্রহণযোগ্য, বড় হলে কমপ্রেস বা রিজেক্ট করা হবে।

### 4.2 Security
- পাসওয়ার্ড bcrypt দিয়ে হ্যাশ করা হবে।
- JWT টোকেন দিয়ে সেশন ম্যানেজমেন্ট, টোকেনের মেয়াদ ২৪ ঘণ্টা।
- শুধুমাত্র অনুমোদিত ইউজার পোস্ট/Claim করতে পারবে (রোল-ভিত্তিক অ্যাক্সেস কন্ট্রোল)।
- ফর্ম ইনপুট স্যানিটাইজ করা হবে (XSS প্রতিরোধ)।
- কন্টাক্ট ইনফরমেশন Private হলে শুধুমাত্র লগইন করা ভেরিফাইড ইউজার দেখতে পাবে।

### 4.3 Usability
- UI হবে সহজ ও পরিচ্ছন্ন; মোবাইল রেসপনসিভ।
- প্রতিটি অ্যাকশনের জন্য স্পষ্ট বাটন ও ফিডব্যাক (সফল/ব্যর্থ মেসেজ)।
- ফর্ম ভ্যালিডেশন ক্লায়েন্ট ও সার্ভার দুই দিকেই হবে।

### 4.4 Reliability
- ডাটাবেস সংযোগ বিচ্ছিন্ন হলে ব্যবহারকারীকে যথাযথ এরর মেসেজ দেখানো হবে।
- ডেটা লস এড়াতে নিয়মিত ব্যাকআপ (ডেভেলপমেন্ট পর্যায়ে ম্যানুয়াল)।

### 4.5 Maintainability
- কোড মডুলার হবে (MVC প্যাটার্ন)।
- API এন্ডপয়েন্টগুলো ডকুমেন্টেড থাকবে।
- পরিবর্তন সহজে করার জন্য কনফিগারেশন ফাইল (.env) ব্যবহার করা হবে।

## 5. Data Requirements (High-Level Entities)

### 5.1 User
- Student ID (unique)
- Full Name, Email, Phone, Department, Batch, Password (hashed)
- Verification Status: Pending / Approved / Rejected
- Role: Student / Admin
- Created At

### 5.2 Post
- Post Type: Lost / Found
- Item Name, Category, Description, Location, Date & Time
- Images (array of URLs)
- Contact Email, Phone, Visibility (Public/Private)
- Status: Open / Claimed / Resolved
- Created By (User ID reference)
- Created At, Updated At

### 5.3 Claim
- Post ID (reference)
- Claimant User ID (reference)
- Claim Message
- Status: Pending / Accepted / Rejected
- Deadline (set by Admin)
- Created At

### 5.4 Notification (optional)
- User ID (recipient)
- Post ID, Claim ID (optional reference)
- Message, Is Read
- Created At

## 7. Assumptions and Dependencies

- বিশ্ববিদ্যালয়ের প্রতিটি শিক্ষার্থীর একটি ইউনিক স্টুডেন্ট আইডি আছে যা নকল করা কঠিন।

- প্রজেক্টটি একটি শিক্ষামূলক ল্যাব প্রজেক্ট, তাই প্রোডাকশন-লেভেল স্কেলিং প্রয়োজন নেই।
